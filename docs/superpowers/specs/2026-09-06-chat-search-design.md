# Поиск по чатам в сайдбаре

**Дата**: 2026-09-06
**Статус**: принят

## Контекст

Список чатов в сайдбаре (`ChatView.vue`) растёт линейно и не имеет способа
навигации, кроме прокрутки. Задача 1.3 просит фильтр по названию чата.

Весь список чатов уже загружен на клиент (`api.listChats()` в `onMounted` и после
каждого стрима), поэтому фильтрация — чисто клиентская операция над имеющимися
данными и не требует ни нового эндпоинта, ни состояния загрузки.

## Решение

Локальное реактивное состояние `search` в `ChatView.vue` и производный от него
`computed`-список, по которому рендерится сайдбар. Запросов к API поиск не делает.

## Критерии приёмки

1. В сайдбаре над списком чатов есть текстовое поле с плейсхолдером «Поиск по чатам».
2. Пустой запрос — показаны все чаты в исходном порядке (свежие сверху).
3. Непустой запрос — показаны только чаты, чей `title` содержит запрос как
   подстроку без учёта регистра; исходный порядок сохраняется.
4. Ведущие и замыкающие пробелы в запросе игнорируются.
5. Если запрос непустой и под фильтр не попал ни один чат — под списком
   показывается строка «Ничего не найдено». У пользователя без чатов при пустом
   запросе этой строки нет: пустой список там — не результат поиска.
6. Создание чата — кнопкой «Новый чат» или автосозданием при первом сообщении —
   сбрасывает запрос, поэтому новый чат виден в сайдбаре сразу.
7. Во время стрима поле поиска остаётся активным; кнопки чатов по-прежнему
   заблокированы, как и было.
8. Поиск не выполняет сетевых запросов.

Пункты 5 и 6 — результат аудита, а не исходной формулировки задачи: без пункта 6
только что созданный чат исчезает из сайдбара, если запрос непустой.

## Реализация

Затрагивается один файл — `front/src/components/ChatView.vue`:

- `const search = ref('')`;
- `const filteredChats = computed(...)` — `title.toLowerCase().includes(query)`,
  где `query = search.value.trim().toLowerCase()`; при пустом `query` возвращается
  `chats.value` без копирования;
- в разметке: `<input v-model="search">` между кнопкой «Новый чат» и списком,
  `v-for` по `filteredChats`, `v-else`-строка «Ничего не найдено»;
- `search.value = ''` в `createNewChat()` и в ветке автосоздания чата внутри `send()`.

CSS: поле поиска обходится глобальным правилом `input` в `style.css`; добавляется
только правило `.no-results` для строки «Ничего не найдено».

`toLowerCase()` корректно приводит кириллицу; `localeCompare` и `Intl.Collator`
для проверки вхождения подстроки не нужны.

## Рассмотренные альтернативы

- **Поиск на бэкенде** (`GET /api/chats?q=`) — отклонён: список уже целиком в
  памяти клиента, серверный поиск добавил бы эндпоинт, дебаунс и состояние
  загрузки без выигрыша. Потолок решения — сотни чатов на пользователя; при их
  появлении фильтр переезжает на бэкенд вместе с пагинацией списка.
- **Fuzzy-поиск (fuse.js и аналоги)** — отклонён: новая зависимость ради проверки
  вхождения подстроки.
- **Не сбрасывать поиск при создании чата** — отклонён: пользователь нажимает
  «Новый чат» и не видит результата, потому что чат не проходит фильтр.

## Тестирование

Разработка по TDD: тесты пишутся первыми и падают на отсутствующем поле поиска.

Уровень — e2e (Playwright, стенд с локальным стабом OpenRouter уже поднят,
см. ADR-0004). Юнит-слоя во фронте нет; заводить Vitest ради одного `computed`
не будем — поведение целиком наблюдаемо через UI.

Новый файл `e2e/tests/search.spec.ts`, общий `beforeEach`: регистрация уникального
пользователя и создание двух чатов с названиями «Кошки» и «Собаки» (название чат
получает от бэкенда из первого сообщения). Три теста, по одному поведению:

1. фильтрует список по подстроке без учёта регистра (запрос «кош» → один чат «Кошки»);
2. показывает «Ничего не найдено», когда совпадений нет;
3. сбрасывает запрос при создании нового чата — новый чат виден сразу.

Существующий `e2e/tests/chat.spec.ts` должен остаться зелёным.
